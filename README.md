# Производственный учёт участка технического контроля (MES)

Система учёта и прослеживаемости для участка технического контроля
электронного производства.

> Демонстрационный репозиторий. Данные предприятия, каталоги дефектов и
> справочники изделий заменены на обобщённые демонстрационные.

---

## Вкратце

Заменяет журнал в Excel и бумажную маршрутизацию партий на участке
контроля:

- ведёт каждую партию по техпроцессу и **не даёт пропустить этап** —
  переходы статусов проверяются на сервере;
- держит **прослеживаемость до конкретного изделия** по серийному
  номеру, а не до партии;
- собирает несоответствия **по каталогу формулировок** — отсюда честная
  аналитика «топ дефектов» и «топ позиций на плате»;
- печатает ярлыки, акты и QR-этикетки **данными из системы**, а не
  руками;
- работает **на планшете в цеху и без сети** — правки уходят на сервер
  сами;
- **не выбрасывает Excel**: двусторонняя синхронизация с общим журналом;
- **интегрирован с корпоративным мессенджером**: единый вход, роли из
  ролей группы чата, уведомления о важных событиях.

Стек: Next.js 16, React 19, TypeScript, Prisma, SQLite, Tailwind,
Docker. ~90 файлов исходников, 24 группы API-маршрутов, тесты
бизнес-инвариантов.

Сделано целиком: постановка задачи, модель данных, интерфейс,
интеграции, развёртывание на планшетах в цеху.

## Быстрый запуск

```bash
cd acts
npm install
npm run db:push        # создать схему
npm run seed:demo      # демонстрационные данные

```

# О проекте подробно

## Задача

На участке технического контроля партии изделий проходят приёмку,
входной контроль, тестирование, выходной контроль и отгрузку. Учёт вёлся
в одном Excel-файле на сетевой шаре. Отсюда типичные проблемы:

- файл правят несколько человек — правки затирают друг друга;
- статус партии знает только тот, кто её вёл;
- несоответствия описываются свободным текстом, поэтому «топ дефектов»
  посчитать невозможно;
- прослеживаемости до конкретного изделия нет — брак ищут по всей партии;
- ничто не мешает отгрузить партию, не закрыв ремонт.

## Что делает система

**Маршрут по техпроцессу.** Партия идёт по фиксированной цепочке
статусов: принят → входной контроль → в работе → выходной контроль → к
отгрузке → отгружен. Переходы проверяются на сервере: тестировщик не
может перепрыгнуть этап или отгрузить партию. Обход доступен старшему и
начальнику и записывается в журнал действий.

**Прослеживаемость до штуки.** Серийные номера вносятся сканом QR-кода
партии, количество считается автоматически. Ярлык несоответствия
вешается на конкретный серийный номер, а не на партию: изделие с
открытым ярлыком не уйдёт на следующий этап. По серийному номеру
поднимается вся история изделия — кто принял, кто тестировал, что нашли.

**Учёт несоответствий.** Формулировка выбирается из каталога, а не
пишется руками — иначе один дефект попадает в журнал десятком разных
фраз. Отдельным полем хранится десигнатор (позиция элемента на плате),
чтобы отвечать на вопрос «какая позиция чаще всего непропаяна».
Исходы ярлыка: ремонт, изолятор, анализ у разработчика, отклонение
разрешено.

**Печатные формы.** Ярлыки несоответствия (3 на лист), акт
несоответствия, акт изъятия, маршрутная карта — заполняются данными
автоматически. QR-этикетки печатаются на термопринтер Godex генерацией
EZPL напрямую, без драйверов и промежуточного ПО.

**Цеховой экран.** Отдельный интерфейс для планшета: работа в перчатках,
крупные кнопки, один экран — одно действие. Ввод серийного номера
открывает карточку изделия.

**Работа без сети.** Приложение ставится как PWA. При потере связи
правки копятся в локальной очереди и уходят на сервер сами при
восстановлении соединения.

**Excel не выбрасывается.** Двусторонняя синхронизация с общим
Excel-журналом: правки из файла импортируются с политикой слияния,
изменения из системы дописываются обратно. Посторонние листы, шапка и
формулы сохраняются, запись атомарная.

**Аналитика.** Показатели периода со сравнением к предыдущему: принято,
отгружено, уровень несоответствий, длительность цикла. Срезы по
изделиям, типам дефектов, этапам и тестировщикам.

**Роли и подписи.** Тестировщик / старший / начальник. Подпись
проставляется автоматически по вошедшему пользователю — ФИО руками не
вводится. Приёмка и отгрузка доступны только старшему и начальнику.
Каждое изменение попадает в журнал действий: кто, что, было → стало.

**Единый вход.** Логин один — в корпоративном мессенджере; учёт
подхватывает его и берёт роль из роли сотрудника в рабочей группе чата.
Отдельных паролей и ручного ведения прав нет. Подробнее — в разделе
«Интеграция учёта и мессенджера».

# Модули

Репозиторий собран как монорепозиторий: основное приложение плюс
вспомогательные сервисы, которые не могут жить внутри веб-приложения.

## `acts/` — основное приложение учёта

Ядро системы. Next.js 16 (App Router) + React 19 + TypeScript,
данные через Prisma в SQLite, интерфейс на Tailwind и Radix UI,
графики на Recharts.

```
acts/
  src/app/          страницы: журнал, карточка акта, цеховой экран,
                    аналитика, продукция, сотрудники, действия
  src/app/api/      REST API — 24 группы маршрутов
  src/components/   интерфейс: журнал, карточка, дефекты, импорт, печать
  src/lib/          бизнес-логика (см. ниже)
  prisma/           схема данных
  scripts/          миграции, бэкапы, демо-данные
```

Ключевое в `src/lib/`:

| Файл | Ответственность |
|---|---|
| `act-transitions.ts` | серверная матрица переходов статусов |
| `invariants.test.ts` | тесты бизнес-инвариантов (Bun) |
| `journal-excel.ts` | импорт и обратная запись в Excel-журнал |
| `folder-sync.ts` | периодическая синхронизация с файлом |
| `statuses.ts` | статусы актов и состояния ярлыков |
| `roles.ts` | роли и права |

Основные сущности: акт (партия), изделие, серийный номер, ярлык
несоответствия, отгрузка, сотрудник, каталог дефектов, запись журнала
действий.

## `localchat/` — корпоративный мессенджер

Локальный мессенджер для работы только внутри сети предприятия: без
обращений к внешнему интернету. Отдельный продукт, включён в
монорепозиторий ради интеграции с учётом и используется с разрешения
автора — в этом проекте моя часть это интеграция, а не сам мессенджер.

Стек: Node.js (Express, Socket.IO, better-sqlite3, JWT, Helmet) на
сервере, React 18 + Vite на клиенте, совместные документы на Yjs +
TipTap, опционально OnlyOffice для офисных форматов. Порт 3780,
разворачивается своим `docker-compose.yml`.

Возможности: профиль с уникальным тегом как единственным
идентификатором, группы с ролями (админ / модератор / участник) и входом
по коду присоединения, упоминания `@тег`, личные чаты между коллегами,
вложения, закрепление сообщений, совместное редактирование документов и
таблиц.

## Интеграция учёта и мессенджера

Две системы работают как одна платформа: общий вход, взаимные переходы и
уведомления.

**Единый вход (SSO).** Сотрудник логинится один раз — в мессенджере.
Учёт берёт его токен (`localchat_token` из cookie либо заголовок
`Authorization`), спрашивает у чата `/api/me` и `/api/groups` и проверяет
членство в рабочей группе. Отдельного пароля в учёте нет.

**Роли из ролей группы чата.** Права в учёте не ведутся вручную, а
выводятся из роли в группе и обновляются при каждом входе:

| Роль в группе чата | Роль в учёте |
|---|---|
| админ | начальник |
| модератор | старший |
| участник | тестировщик |

Учётная запись связывается с чатом по тегу (`chatTag`). Ответы на
неуспешный вход конкретные: не вошёл в чат — предложение войти; вошёл,
но не состоит в группе — «попросите администратора группы добавить вас».

**Переходы и дип-линки.** В учёте есть кнопка перехода в чат, в чате — в
учёт. Ссылка вида `/?act=<номер>`, отправленная в чат, открывает сразу
карточку нужного акта.

**Уведомления** — через `chat-bridge/` (ниже).

Настраивается переменными `CHAT_URL`, `CHAT_PUBLIC_URL`, `CHAT_GROUP_ID`,
`CHAT_GROUP_NAME`. Если они не заданы, интеграция просто выключена и
учёт работает самостоятельно со входом по PIN.

Код интеграции: [`acts/src/lib/chat-sso.ts`](acts/src/lib/chat-sso.ts),
[`acts/src/app/api/auth/sso/`](acts/src/app/api/auth/sso/).

## `chat-bridge/` — мост уведомлений в мессенджер

Отдельный маленький сервис на Node.js без зависимостей. Раз в
`POLL_SECONDS` читает журнал действий учёта через `/api/logs`, находит
новые события нужных типов и отправляет их сообщением в группу
мессенджера от имени бота.

В чат попадают: массовый дефект, помещение изделия в изолятор, отгрузка
акта, обход техпроцесса (кто и что). Отправленные записи запоминаются в
`.bridge-state.json` — повторов нет, старые события не рассылаются.

Ничего не меняет ни в учёте, ни в мессенджере — выключается в любой
момент.

## `app/` — ранний прототип на FastAPI

Первая версия учёта на Python (FastAPI + SQLAlchemy + Jinja2), с которой
проект начинался. Оставлен как история проекта; актуальная система —
в `acts/`.

## Инженерные решения, о которых стоит спросить

- **Матрица переходов на сервере, а не в UI.** Клиентская проверка —
  подсказка, а не гарантия; статус меняется только через серверную
  матрицу с обязательной подписью.
- **Счётчики выводятся из событий.** Количество в ремонте и на анализе
  не хранится полем, а считается из открытых ярлыков — иначе цифры
  расходятся с фактом.
- **Слияние с Excel, а не импорт.** Файл не может откатить прогресс
  статусов; сопоставление строк идёт по ключу «номер акта + изделие», а
  не по номеру строки, поэтому вставка строк ничего не сдвигает.
- **Каталог дефектов вместо свободного текста** — единственный способ
  получить честную аналитику по типам несоответствий.
- **Прослеживаемость до серийного номера, а не до партии** — иначе при
  обнаружении брака под подозрением вся партия целиком.
- **SQLite, а не PostgreSQL.** Объёмы участка не приближаются к пределам
  SQLite; реальные риски — миграции и бэкапы, они и в приоритете.
